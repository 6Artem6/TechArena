# ADR-013: Стандарты документации и качества кода

**Статус:** Принято  
**Дата:** 2026-10-13

## Контекст

Проект разрабатывается в команде и должен быть понятен новому участнику без устного объяснения. Нужны единые стандарты: стиль кода, docstring'и, комментарии, README в каждом модуле и общий реестр документов.

---

## Решение

### Стиль кода

**Форматирование:** black + isort (настроено в `pyproject.toml`, ADR-001).  
**Типизация:** mypy strict=false, но все публичные функции и методы должны иметь аннотации типов.  
**Именование:** snake_case для функций/переменных, PascalCase для классов, UPPER_CASE для констант.

### Docstring'и — Google Style

Обязательны для:
- Всех публичных классов
- Всех публичных методов и функций
- Всех модулей (верхний docstring файла)

```python
def analyze_blast_radius(
    change_spec: ChangeSpec,
    graph: DependencyGraph,
    max_depth: int = 6,
) -> BlastRadius:
    """Вычисляет blast radius — множество узлов, затронутых изменением.

    Выполняет двунаправленный BFS по графу зависимостей, начиная
    от узлов, соответствующих change_spec. Обход идёт во все стороны
    (вверх по CONTAINS, вбок по CALLS/USES_DTO, вниз к методам).

    Args:
        change_spec: Описание изменения (файл, класс, метод).
        graph: Граф зависимостей репозитория.
        max_depth: Максимальная глубина обхода (защита от зависания).

    Returns:
        BlastRadius с множеством затронутых NodeId.

    Raises:
        NodeNotFoundError: Если стартовый узел не найден в графе.

    Example:
        >>> spec = ChangeSpec(file="ts-order-service/.../OrderServiceImpl.java")
        >>> result = analyze_blast_radius(spec, graph)
        >>> len(result.affected_nodes)
        12
    """
```

### Комментарии в коде

Комментарий объясняет **ПОЧЕМУ**, не **ЧТО**. Правила:

```python
# ПЛОХО: итерируем по узлам графа
for node in graph.nodes():
    ...

# ХОРОШО: подавляем CONTAINS-рёбра при обходе вверх —
# иначе изменение любого метода затягивает весь сервис целиком
for node in graph.nodes():
    ...
```

Обязательные комментарии:
- Нетривиальные условия и граничные случаи
- Обходы известных багов библиотек (с указанием issue)
- Магические числа (почему `max_depth=6`, почему вес `USES_MAGIC_CALL=1.5`)
- Места, которые намеренно упрощены (с пометкой `# TODO: ...` и причиной)

### README.md в каждом модуле

Обязательно иметь `README.md` в:

| Директория | Содержимое README |
|---|---|
| `/` (корень) | Быстрый старт, ссылки на docs/, схема сервисов |
| `services/engine-api/` | Что делает, как запустить, endpoints, env vars |
| `services/worker-service/` | Что делает, очередь задач, env vars |
| `services/ml-service/` | Модели, API endpoints, как добавить модель |
| `services/ui-service/` | Как запустить dev, как собрать, переменные |
| `src/domain/` | Доменная модель: узлы, рёбра, алгоритмы |
| `src/adapters/` | Список адаптеров, как добавить новый |
| `src/adapters/parsers/` | Поддерживаемые языки, как добавить язык |
| `docs/` | Реестр документов (см. `docs/README.md`) |

### Mermaid-схемы

Mermaid используется везде, где текст хуже передаёт структуру:

| Тип схемы | Когда использовать | ADR с примером |
|---|---|---|
| `flowchart` | Алгоритмы, fallback-цепочки | ADR-003 |
| `sequenceDiagram` | Взаимодействие сервисов во времени | HOW_IT_WORKS |
| `classDiagram` | Доменная модель, иерархии | ADR-002, ADR-006 |
| `graph` | Топология сервисов | ADR-009 |
| `gantt` | Фазы реализации | PLAN |
| `erDiagram` | Схема БД | ADR-008 |

Правила:
- Схема идёт **до** текстового описания, не после.
- Каждая схема имеет заголовок `%%{ title: "..." }%%` или предшествующий `###`.
- Схемы в ADR — для архитектурных решений; схемы в `HOW_IT_WORKS` — для потоков данных.

### Общий реестр документов

`docs/README.md` — единая точка входа. Содержит:
- Карту всех документов с однострочным описанием
- Mermaid-схему связей между документами
- Ссылки на внешние ресурсы (GitHub issues, репо)

Каждый ADR в шапке содержит ссылки на связанные ADR:
```markdown
**Связанные:** ADR-002 (схема графа), ADR-005 (обход), ADR-011 (URL-резолвинг)
```

### Объяснение работы приложения

Отдельный документ `docs/HOW_IT_WORKS.md` (не ADR) описывает:
- Два главных потока: индексация и запрос blast radius
- Sequence-диаграммы для каждого
- Как данные проходят через слои архитектуры

Дополнительно: `docs/ARCHITECTURE.md` — статичная схема компонентов.

## Последствия

- PR без docstring'ов на публичных API — не принимается.
- Новый язык парсера = новая секция в `src/adapters/parsers/README.md`.
- Каждый новый ADR обновляет `docs/README.md` (реестр).
